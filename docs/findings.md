## Architecture

| Approach | Decision |
|---|---|
| INI/shader mod | Fits eventual validated shader replacements and targeted labels. INI commands lack general API timings and nonblocking timestamp ownership at submission boundaries. |
| Independent DX11 extension | A second wrapper would compete for device/context ownership. Use external ETW for independent measurements in vanilla and every other configuration. ReShade’s DX11 handling is a useful reference for event coverage and lifetime. |
| Narrow XXMI patch | Selected for native capture. Adds probes to known wrapper boundaries, uses passthrough interfaces for queries, and relies on the existing launcher and command-list behavior. This lets the profiler record selected XXMI scopes without the hunting overlay. |
| Hybrid | Keep as a distribution option if measured experiments justify shader changes. The current package pairs the narrow native patch with external capture and analysis tooling. |

## Roscaelifer and interpretation

The official 3.0 PC upgrade FAQ distinguishes DX11 and DX12 eligibility and graphics options. Community reports describe Roscaelifer slowdown and uneven GPU use, with variation across versions, settings, views and systems. No verified trace establishes a pass, resource or engine bottleneck. Avoid inferring causality from utilization alone. [Official PC FAQ](https://zenless.hoyoverse.com/en-us/news/165408) · [Low GPU utilization report](https://www.reddit.com/r/ZZZ_Official/comments/1ucftwa/low_gpu_usage_in_roscaelifer/) · [Roscaelifer frame-rate reports](https://www.reddit.com/r/ZZZ_Official/comments/1v7vukg/any_pc_players_here_can_you_confirm_that/)

The first analysis compares uncapped PresentMon GPU busy with frame intervals at two rendering resolutions. The native run helps test whether longer frames coincide with higher GPU envelopes, large submitted workloads, slow Map/GetData/Present or resource operations, or extra XXMI work. A repeatable gap between CPU frame interval and visible graphics API time calls for CPU sampling or scheduler data before attributing it to a particular engine subsystem. Collect a focused upstream frame analysis if a GPU workload dominates and its resource dependencies must be identified.

## Capture coverage

- Native frame intervals are between consecutive wrapped Present starts on one foreground swap chain. They include elapsed waiting and CPU work outside the wrappers. Present time comes from the original DXGI call. PresentMon provides an independent frame interval, CPU busy, GPU busy, and display timing where supported.
- CPU timers are inclusive and can overlap. Counts describe wrapper requests, including skipped or deferred draws. Indexed and vertex totals use requested direct draw counts and multiply instanced arguments. Indirect draws provide call counts. The report extrapolates sampled CPU time per API and keeps the actual sample count. Driver Map is timed separately from XXMI map handling. Stall candidates are timings above a configured threshold. They can include scheduling delay and do not prove a GPU wait.
- API CSV records up to 32 participating threads. End-of-frame collection tries to take each thread’s shard. A contended shard moves to the next frame, and ending the capture drops in-flight scopes. CPU wrapper sums can include simultaneous threads, nested calls, and profiler overhead.
- DX11 GPU timestamps use a bounded asynchronous ring. Retrieval skips early frames and uses `D3D11_ASYNC_GETDATA_DONOTFLUSH`. Disjoint, unavailable and undrained samples are reported. GPU envelope is the timestamp interval on the immediate context. It can include queue starvation. Workload segments use observed forwarded draws, dispatches, copy/update/resolve, clear and command-list operations. They can include other work between selected markers. The target label uses the first wrapped RTV or depth-only DSV for the current sampled bind sequence. Changes outside these wrapper paths can invalidate the label. Segment caps favor earlier workloads. Use lower sampling intervals or targeted Level 3 only when needed.
- The upstream shader hash can be zero when tracking is disabled or unavailable. Level 3 uses the observed upstream hash, which can represent the pre-replacement shader. Repeated shader requests are observations of matching handles with zero class instances on the current request. They cannot establish redundancy across ClearState, command-list execution, replacement or changes from another tool.
- Memory samples use per-process DXGI local and nonlocal budgets on adapter node 0. Buffer size is the sum of requested bytes for wrapped CreateBuffer calls. The first build counts creates, maps, updates and copies. Allocation lifetimes, complete upload byte estimates, unique shaders per frame, primitive counts, adapter-wide utilization and full per-pass identification still need evidence or finer instrumentation.
- Boundary bookkeeping time is measured. It excludes per-call probe overhead and GPU query impact outside that boundary. Compare repeated `profiler-off`, `profiler-l1` and `profiler-l2` PresentMon runs for the total effect. The cross-compiled DLL and stock DLL also differ in toolchain, so attribute stock vs profiler-off changes to the entire replacement build. The profiler exports after the measured interval and can briefly pause rendering while writing files.
